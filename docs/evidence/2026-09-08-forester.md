## The arc at the real boundary

In the playground sandbox `.playground/five`, whose Grove profile has
overlays on and whose adapter is the sample project's own, with five seats
`w1`..`w5` already planned by an earlier run. A four-item plan was written
into the sandbox project and `parallel: 2` into its local file.

```text
$ forester plan
  api-notes-count  ready    no dependencies
  web-heading      ready    no dependencies
  web-count        blocked  waits for api-notes-count
  readme-notes     ready    no dependencies
  items 4 · done 0 · active 0 · ready 3 · blocked 1 · failed 0

$ forester next
  assign  api-notes-count  owns app/api/**
  assign  web-heading      owns app/web/**
  hold    readme-notes     budget full (2)
  would assign 2/2; changes nothing

$ forester assign --apply          → two Dryad seats, worktree 1/1 created, env 1/1 each
  assigned 2/2 · slots 2/2

$ dryad report api-notes-count --status done
$ forester next
  assign  readme-notes     owns README.md
  hold    web-count        claim app/web/** intersects app/web/** of web-heading (active)
  would assign 1/1; changes nothing

$ forester assign --apply          → readme-notes seated;   assigned 1/1 · slots 2/2
$ dryad report web-heading --status done
$ forester assign --apply          → web-count seated;      assigned 1/1 · slots 2/2

$ forester status
  slots    2/2
  waiting  0 ready · 0 blocked
  done     2/4
  failed   0
  outside  5 seats not in the plan  w1, w2, w3, w4, w5
```

Every seat Forester created is a real Dryad seat with a real overlay env
made by the sandbox adapter (`dryad status`: seats 9, worktrees 9/9 present,
envs 9/9 tracked, four `by forester`). The claim rule held `web-count` while
`web-heading` was active on the same path and released it after the done
report. The budget held `readme-notes` at 2/2 and released it after the
first done report. The five seats outside the plan took no slot and were
counted.

`dryad status` exits 1 in that sandbox because the five earlier seats' envs
are past `stale_after`; that predates this round and is not Forester's.

### The arc with two real Claude Code sessions

Same sandbox, same plan, the two remaining items `web-count` and
`readme-notes` seated but without a session. Local file: `parallel: 2`,
`tool: claude`, `command: [claude, "{task}", --permission-mode,
acceptEdits]`. Each item's task line ends with the Dryad instruction to
commit on the branch and run `dryad report "$DRYAD_ID" --status done`. A
watcher script stood in for a person: it polled `status --json`, and
whenever a session was `needs-input` it attached over the socket, read the
replayed screen, and pressed Enter on a permission prompt.

Three runs were needed, and each of the first two found a defect that is now
a guard:

1. Both sessions sat at `starting` for six minutes. The screen, read
   through the socket, showed Claude's "Allow external CLAUDE.md file
   imports?" dialog (the sandbox's CLAUDE.md imports the catalog's
   AGENTS.md), with "No, disable" selected, before any prompt was
   submitted, so no hook could fire. The events file also carried the
   previous run's `SessionEnd`. Fixes: the events file is truncated per
   launch, and a session still `starting` whose screen ends on a
   confirm-or-cancel line is reported `needs-input`.
2. Still `starting`: the fallback compared "Enter to confirm" with spaces,
   and the byte stream reads "Entertoconfirm" because the TUI draws spaces
   as cursor moves. Fix: compare with every space removed.
3. The run below.

```text
[0s]  web-count=running readme-notes=running        (dialog answered, UserPromptSubmit fired)
[9s]  both needs-input                              (Notification permission_prompt: a Bash command)
[12s] web-count  "Do you want to proceed? ❯ 1. Yes"  → Enter
[14s] readme-notes same                             → Enter
…     five more prompts, each answered the same way through the socket
[60s] readme-notes: "dryad report … --status done"  → Enter
[63s] readme-notes=closed:129/done
[71s] web-count: "dryad report … --status done"     → Enter
[74s] web-count=closed:129/done

events  web-count     UserPromptSubmit Notification permission_prompt ×3 SessionEnd
        readme-notes  UserPromptSubmit Notification permission_prompt ×2 SessionEnd
seats   web-count +1 commit a78f7cc "web: show notes count from the api on the page"  done
        readme-notes +1 commit d6cb3cc "Document the count field on /notes"          done
status  slots 0/2 · done 4/4 · failed 0 · outside 5 · serve pid … sessions 2, both closed 129
serve   "closing (seat reported done)" for both; SIGINT removed snapshot and socket
```

Exit 129 is SIGHUP: serve closes a session by ending the process once its
seat reports done, never by typing into it. The trust seed was `seeded` on
the first run and `already` after, in `~/.claude.json`, for the two seat
worktrees. The two sessions' own warning "Transcript saving is off,
inherited CLAUDE_CODE_CHILD_SESSION marker" came from serve being started
inside this Claude Code session; serve now drops that variable too.

### One item under Codex

A fifth item, `changelog-codex`, with `tool: codex` and the template
`[codex, "{task}"]`, on the same serve. Codex asked nothing, created the
file, committed `f0266d7`, ran `dryad report --status done`, and serve closed
the session with exit 0, all in 30 s. Its session state read `starting` the
whole time: no hooks are installed for Codex, and the screen fallback only
recognises a confirm-or-cancel line. Completion did not depend on that,
because done is the Dryad report. What a tool other than Claude Code lacks
under serve today is the running / idle / needs-input reading, not the arc.

`forester hooks --apply` on this machine wrote four stores: Codex's
`hooks.json` under the `CODEX_HOME` this shell carries, a file of Forester's
own under `~/.grok/hooks/`, one entry per event in `~/.cursor/hooks.json`
next to the entries Orca had already put there, and an OpenCode plugin
under `OPENCODE_CONFIG_DIR`. Then one item per tool in the sandbox, under
the same serve, with the watcher answering what the screen asked:

| Tool | Session states seen | Prompts | Done | Time |
| --- | --- | --- | --- | --- |
| codex | needs-input (screen: "Hooks need review", answered "Trust all and continue") → starting → running → closed 0 | one, once per store | +1 commit, reported done | 49 s |
| grok | running → closed 0; events `user_prompt_submit`, `pre_tool_use` ×12, `stop` ×2 | none | +1 commit, reported done | 21 s |
| opencode | running → closed 0; plugin events `UserPromptSubmit` ×11, `Stop` | none | +1 commit, reported done | 36 s |
| cursor-agent | starting → needs-input, then a browser login flow | see below | no | — |

The Grok run also showed the earlier defect: the first Grok item finished
while its state read `starting`, because Grok names the event
`user_prompt_submit` under `hookEventName`. The mapper now compares names on
letters only, with that payload as the test sample.

Cursor Agent under serve showed "Press any key to log in…", and a key press
opened a browser login link, although `cursor-agent status` from the same
shell, from a detached process, and from inside the seat worktree in a
pseudo-terminal all reported logged in and went straight to its workspace
trust menu. The difference between those probes and a serve session was
not found in the time given. What serve did do is show the session as
needs-input with the login link on its screen, which is the attended
model's answer; whether a person completing that login through `attach`
lets the session proceed was not measured.

## Not measured

- Cursor Agent to done under serve, for the reason above.
- `attach` from a real terminal by a person (raw mode, resize, Ctrl-]). The
  socket protocol was exercised by a script, not by hands.
- A plan where a person, not this session, judges whether `forester plan`
  is readable. That remains the first evidence the design asks for.
- Claims against what workers actually changed. Dryad's `overlaps` still
  reports that; Forester does not compare the two yet.
- serve after a machine sleep, a crashed serve leaving a snapshot (`status`
  shows it as stale), and two serves for two projects at once.
