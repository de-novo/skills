## A manual run that seated real agents

A person ran this once on the same day. It is not an automated check, and since
the launcher is outside Dryad by design, it does not go into Dryad's regression
tests. This record is one observation of "does the seat contract work as it is
with a real tool".

Setup: one temporary repository with `runtime-profile.yml` (`overlay: none`) and
`dryad-profile.yml` (no `worktrees` section, everything adopted), a
`.agents/skills/dryad` symlink, and a short `AGENTS.md`. The repository was
registered with a desktop worktree manager app, the app created the worktrees,
and Dryad adopted them. The seat was handed over by sending one `seat --shell`
line into the shell the app opened and appending the tool after it.

```bash
de-novo skills dryad plan w1 --task-file ../w1-task.md --worktree <app-made-path> --by claude --apply
# app shell:  eval "$(de-novo skills dryad seat w1 --shell --project <baseline>)" && claude --dangerously-skip-permissions "$(cat ../w1-task.md)"
```

The task text is six lines. Echo the environment variables and read the skill,

### The next day: two improvements and two visual seats (2026-09-07)

  0 after a rejection, finish not blocked. Stub tests 2/2, guard red 1 each.

**One blocker, a real seam problem.** Both seats were rejected by their tool on
the first attach: "image tag must equal the full revision". That tool binds an
env to **one worktree and one revision**, records the caller cwd's HEAD at create
time, and rejects an attach tag that differs from that revision. Grove does
create at plan time (before the seat commits, from the baseline). The two models
were out of step; it is not a defect in Dryad or Grove. It was solved in the
adapter. Before attach, if the recorded revision differs from the image
revision, it destroys the env, recreates it from the caller's worktree
(`GROVE_CALLER_CWD`) with `create --revision <sha>`, and then attaches. The
first attach loses nothing, and a re-attach on a new revision resets the env.
That is exactly their tool's "one env, one revision" rule. The first attempt
(re-running only `create --revision`) was rejected again with "already belongs to
another worktree or revision", and the second fix was correct. The two seats
pinned this cause exactly, though it was not in their briefs, and reported
blocked; after the adapter was fixed, re-running the same command let Grove
recover the pending and confirm it. Throughout, Canopy and Dryad status showed
`stalled` and in-flight as they were.

### What came out of running verify against real adapters (2026-09-07)

`overlay verify` ran on the day it was made against the two adapters written
before it, and found three things. Two were defects in an adapter; one was **a
defect in verify itself**.

| What | Where | Result |
| --- | --- | --- |
| create is not idempotent | the lab's wrapper adapter | Something the contract requires so that a retry after an abort works. Earlier runs had done create only once per env, so they had never stepped on it. Fixed in the adapter to "if the environment is already mine, report success" |
| It picks the attach service without regard to the image | verify | It always attached `attachable[0]`, so someone who supplied another service's image could not pass the attach cases. `--service` was added, and without it the service name is read from the image reference |
| It demanded something outside the contract from the adapter | verify | `overlay.attachable` is a front-door rule and the adapter does not read the profile. Counting an adapter that accepts an undeclared service as a failure was changed to reporting it |

Before the fixes the lab adapter was 4/6; after them, with the image and the
service matched, it is **10/10**. One remaining rule showed up in the run. With
an adapter that binds to a revision, **verify has to be run from the checkout
that produced the image**. Run from another directory, that adapter legitimately
rejects the attach. It is written in the adapter reference document.

### A port collision: the thing Grove tries to prevent happened to us (2026-09-07)

After verify ran on the static site, every name in the lab returned 502. Inside
the cluster it was 200, by node IP it was 200, and from the lab load balancer to
the node it was 200; only from the host it was 502. The 502 body named the
culprit. `no overlay for <web-host>:8080` — that was **the static site's hostname
router**, not the lab gateway. The site adapter's create starts that router,
verify's create ran it, and the router was bound to `127.0.0.1:8080` while the
lab gateway was bound to `*:8080`, so the router intercepted loopback traffic.

Two projects each chose the same 8080 as their "project-owned listener", and
**neither declared that port in `addressing.ports.blocks`.** A skill whose point
is to remove ports by using names had left its own listener's port outside the
register and collided. The site router was moved to 8081 and declared in the
profile as `proxy: 8081`. Since then, with both projects up together, the site's
verify and the lab's names are all normal.

What came out of this: now that Dryad holds this machine's project index, Grove
can **check for machine-level collisions between declared ports**. It is not
implemented yet; it is a candidate.

### An adoption trial: planting it myself on a repository I had never opened (2026-09-08)

"Can somebody else do it from the documents alone" is the box that stayed empty
because it needs another person. Instead, conditions were set and imposed on
myself. **Take only the published skill documents as instructions, do not go
looking in the internal code for the answer, write down each place I got stuck
as it happened, and score the end with `verify` and one seat.** The target is an
in-house monorepo (two services, three libraries) I had never opened, cloned
into the lab. The original checkout was not touched.

The result: the profile was planted, one seat was seated, and that seat put in a
real improvement and verified it. The procedure **led me wrong in two places,
and both were fixed** (`cc27882`).

| Step | Result |
| --- | --- |
| Finding the services | No friction. All three libraries had a `dev` script, but the procedure warned about that trap in advance |
| Port and health | **Friction 1 (serious).** The procedure puts "make one request" (step 2) before "establish engine ownership" (step 5). Following it, I requested an endpoint named after a database first. It turned out harmless (the handler runs no query, and the app does not read that environment file), but that could not be known before the request |
| reflect | **Friction 2.** The first measurement was wrong. The restart had failed, so I nearly measured a service that was not running and read it as "not reflected". Looking at the log caught it |
| Backend, engines, addressing | No friction. The names resolved but returned 404, and `proxy` was left empty, following the evidence that there is no listener |
| Overlay judgment | **No.** There are two services, but there is no isolated build or routing and the ports are literals in the source. `overlay: none`, as the procedure says. That is the honest answer for this project |
| One seat | The defect that showed up while planting ("the API port can only be changed in the source") was handed over as the task itself. The seat made it read `PORT`, and a person ran two instances on 3002 and 3102 at the same time and confirmed 200 on each |

Two fixes went into the procedure. **Read what a health path reaches before
requesting it** (the endpoint's name is not evidence. Follow the handler, and
the environment file the service actually reads. If the candidate is only behind
a datastore, do step 5 first.) And **confirm the service is alive at both ends
of the comparison when measuring reflect** (a failure response from a service
that is not running looks exactly like an edit that was not reflected).

Planting alone produced three facts the repository did not hold: that the API
port can only be changed in the source, that the project's `dev` command does
not start the API at all (that app has no `dev` script), and that the default
database name is generic enough for two projects on one machine to share it. The
first of those was fixed by the seat that day.

The remaining limit, stated honestly: I am the person who wrote these documents,
so I cannot fully play "someone seeing it for the first time". What this trial
proves is that **the procedure is executable end to end on a repository never
opened before, and that running it exposes defects** — not a person's learning
time.

### What cannot be measured and what will not be measured

- **The :80 listener.** It needs root on macOS, and `sudo` on this machine asks
  for a password. The router listens on 8080. "You do not memorize ports" is
  complete only when the one port left on the machine is gone too, and that is
  an operational decision to run the listener as root, not Grove code.
- **The productivity effect.** Time saved or conflicts reduced is not something
  this repository claims, and it is not something a day of running can measure.
  The product direction document says the same thing.
- **Regression tests with real agent tools.** They need credentials and the
  tools, and the launcher is outside by design. The harness above covers the
  contract side, and the three manual runs cover the tool side.
- Concurrent adapter execution on a shared backend (k3d, compose). The same
  boundary as before.
- The liveness of a lock held by another host. The registry is machine-local, so
  it is only shown as `unknown`.
