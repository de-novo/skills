## 실제 에이전트를 자리에 앉힌 수동 실행

같은 날 사람이 한 번 실행했다. 자동 검사가 아니며, 런처는 설계상 Dryad 밖이므로
Dryad의 회귀 검사에는 들어가지 않는다. 이 기록은 "자리 계약이 실제 도구에
그대로 먹히는가"에 대한 한 번의 관측이다.

준비: 임시 저장소 하나에 `runtime-profile.yml`(`overlay: none`)과
`dryad-profile.yml`(`worktrees` 절 없음, 전부 입양), `.agents/skills/dryad` 심링크,
짧은 `AGENTS.md`. 데스크톱 워크트리 관리 앱에 이 저장소를 등록하고, 앱이
워크트리를 만들게 한 뒤 Dryad가 입양했다. 자리는 앱이 연 셸에 `seat --shell`
한 줄을 보내고 그 뒤에 도구를 붙이는 방식으로 넘겼다.

```bash
de-novo skills dryad plan w1 --task-file ../w1-task.md --worktree <app-made-path> --by claude --apply
# app shell:  eval "$(de-novo skills dryad seat w1 --shell --project <baseline>)" && claude --dangerously-skip-permissions "$(cat ../w1-task.md)"
de-novo skills dryad plan w2 --task-file ../w2-task.md --worktree <app-made-path> --by codex --apply
# app shell:  eval "$(de-novo skills dryad seat w2 --shell --project <baseline>)" && codex --dangerously-bypass-approvals-and-sandbox "$(cat ../w2-task.md)"
de-novo skills dryad status
de-novo skills dryad finish w1 --apply && de-novo skills dryad finish w2 --apply
```

작업 본문은 여섯 줄이다. 환경변수를 echo하고 스킬을 읽고, `seat --json`으로 자기
브랜치를 확인하고, NOTES.md에 한 줄을 붙여 그 파일만 커밋하고, `report done`을
치고, 커밋 해시를 답한 뒤 멈춘다. 푸시와 finish는 금지했다.

| 관측 | w1 (Claude Code) | w2 (Codex) |
| --- | --- | --- |
| `DRYAD_ID` `DRYAD_PROJECT` 도달 | 도구가 echo로 출력 | 도구가 echo로 출력 |
| 스킬 읽음 | 읽음 | 읽음(+79줄 출력) |
| `seat --json`으로 브랜치 확인 | w1 | w2 |
| 커밋 | `d26d654 w1: note`, NOTES.md만 | `4623dfe w2: note`, NOTES.md만 |
| `report done` 자기 보고 | 저널에 `seat report done: NOTES.md updated` | 같음 |
| 푸시·finish 안 함 | 지킴 | 지킴 |
| `dryad status` | `reported done 2`, `+1` 둘, exit 0 | |
| `finish --apply` | 입양 워크트리 유지, 브랜치 유지, 자리 제거 2/2 | |

사람이 개입한 곳 둘. 두 도구 모두 처음 여는 디렉터리에 신뢰 확인을 띄웠고,
사람이 앱 터미널에 키를 보내 답했다. 이건 런처의 일이고 Dryad는 모른다. 앱의
`tui-idle` 대기는 Codex가 아직 작업 중일 때 한 번 조용한 구간을 유휴로 판정했다.
완료 판정을 프로세스나 화면이 아니라 작업자의 `report done`으로 두기로 한 결정이
여기서 실제로 값을 했다. Dryad `status`를 폴링해 `done`을 기다리는 것으로 충분했다.

두 도구는 자리에서 전권 플래그로 실행했다. 임시 저장소였기 때문이며, 어떤
권한 정책으로 앉힐지는 런처와 사람의 값이다.

## 실제 프로젝트에서 overlay까지: 이름만으로 두 자리

같은 날 저녁, 실제 브랜드 사이트 저장소(TanStack Start, Vite dev 서버)에서 실행했다.
먼저 `overlay: none`으로 자리 다섯 개(콘텐츠, 라우트, 캡처, 전후 그래픽 둘)를
돌렸고, 그때는 자리마다 dev 서버 포트를 지시서에 손으로 나눠야 했다. 그것이
Grove를 안 쓴 것임을 확인한 뒤, 프로젝트에 overlay 어댑터를 심고 두 자리를 다시
돌렸다.

프로젝트가 소유한 것: `tools/dev-overlay.mjs`(Grove overlay 계약의 process
backend. `attach <env> web --image acme/web:<sha> -- --worktree <path>`가
그 워크트리의 Vite를 빈 loopback 포트에 띄우고 기록한다. status는 실제 프로세스와
HTTP 200을 관측한다. 이미지 sha가 워크트리 HEAD와 다르면 거부한다),
`tools/dev-router.mjs`(`web--<env>.acme.localhost` → 기록된 포트,
`web.acme.localhost` → baseline :3000. 8080에서 듣는다. `proxy: project`),
프로파일의 `overlay.attachable: [web]`, `runtime.commands.overlay`.

Grove 경로를 사람이 먼저 한 바퀴 돌렸다.

| 단계 | 관측 |
| --- | --- |
| `overlay create t1 --apply` | postcondition 1/1 |
| `overlay attach t1 web --image …<sha> --apply -- --worktree <w5>` | postcondition 1/1 (status 6회 관측 뒤 ready), upstream `127.0.0.1:61158` |
| `overlay status` | environments 1, attachments 1, drift 0, exit 0 |
| `http://web--t1.acme.localhost:8080/work/de-novo-skills` | 200, w5 브랜치에만 있는 내용을 서빙 |
| `http://web.acme.localhost:8080/` | 처음 502(라우터가 127.0.0.1로 붙었는데 baseline은 ::1에만 있었다) → localhost로 고친 뒤 200 |
| `overlay destroy t1 --apply` | postcondition 1/1, Vite 프로세스 0, state 비움 |

그 다음 자리 둘. w6(Claude Code)은 `/work` 색인 시트, w7(Codex)은 헤더의 조건부
`WORK` 링크. 지시서에는 포트가 한 줄도 없다. 작업자는 커밋 → HEAD sha로
`overlay attach` → 자기 이름으로 curl → `overlay status` exit 0 → `report done
--session`.

| 관측 | w6 Claude Code | w7 Codex |
| --- | --- | --- |
| `overlay create` (plan 시 Grove가 실행) | 1/1 | 1/1 |
| `overlay attach` postcondition | 1/1, 이미지 sha = 워크트리 HEAD | 1/1, 이미지 sha = 워크트리 HEAD |
| 자기 이름으로 확인 | `/work` 200, `/work/does-not-exist` 404 | `/` 200, 헤더 `href="/work"` 정확히 1 |
| 격리 | w6 홈에는 헤더 링크 0 | w7 `/work`는 404 |
| baseline 이름 | `href="/work"` 0, 200 (두 자리의 변경이 새지 않음) | |
| `report --session` | 남김 | 남김 |
| `finish --apply` | env 1/1 destroyed, 워크트리·브랜치 유지 | 같음 |
| 종료 후 | Grove environments 0, 어댑터 Vite 프로세스 0, 라우터 내림, baseline :3000 그대로 | |

사람이 개입한 곳: 어댑터와 라우터 작성, 라우터의 baseline 주소 수정 한 번. 신뢰
확인은 이번엔 뜨지 않았다(같은 저장소 root를 이미 신뢰). 두 도구 모두 `DRYAD_SKILL`로
스킬을 읽었고 `seat --task`로 첫 프롬프트를 받았다.

### 공유 엔진: 데이터 격리, 그리고 사고 하나

임시 프로파일 둘(`dryad-proof-a`, `dryad-proof-b`, 각각 pg 데이터베이스 하나와 redis
prefix)에 `setup`을 실행했다. 엔진은 이미 돌고 있었다.

| 관측 | 결과 |
| --- | --- |
| `setup` a, b | engines 2/2, DBs 1/1 씩 |
| a가 자기 DB에 테이블·행 생성 | 1 |
| b가 a의 DB에 접속 | 거부: CONNECT 권한 없음 |
| b가 a의 테이블 select / create / drop | 전부 거부 (접속 단계에서) |
| a의 데이터 | 그대로 |
| 정리 | 두 DB와 role drop, 잔여 0 |

**사고.** 같은 실행에서 `setup`이 돌고 있던 `dev-pg16`과 `dev-redis7`를 재생성했다.
컨테이너 ID가 바뀌었고, 데이터는 named volume이라 남았으며, 선언하지 않은
`dev-mysql8`은 그대로였다. compose 파일의 config hash가 엔진 기동 시점과 달라져
`up -d --wait`가 재생성한 것이다. infra README가 경고해 둔 경우가 실제로 일어났다.
같은 밤 `setup`과 `infra up`에 `--no-recreate`를 넣었다(`7040c93`). docker shim으로
두 진입점의 compose 인자를 세는 테스트 2/2, 가드를 빼면 red 1, 그리고 공유 엔진에
플래그를 붙여 `setup`을 다시 실행해 컨테이너 ID가 그대로인 것 2/2. 플래그가 실제
config drift 아래에서 재생성을 막는지는 공유 엔진에 drift를 일부러 만들 수 없어
compose 문서의 의미에 기댄다.

### 다음 날: 두 개선과 시각화 자리 둘 (2026-09-07)

overlay 자리 두 개를 앉히며 드러난 마찰 둘을 Grove에 넣고(`8ec6389`) 실제 어댑터로
쟀다.

- **`GROVE_CALLER_CWD`.** 작업자가 attach마다 `-- --worktree "$PWD"`를 넘겨야 했다.
  Grove가 호출자 디렉터리를 프로젝트 명령의 환경변수로 넘기고, 어댑터가 그것을
  기본값으로 쓴다(검증은 어댑터 몫). 측정: 자리 워크트리에서 플래그 없이 attach →
  기록된 worktree가 그 경로, 이름으로 200. baseline 디렉터리에서 attach → 거부.
- **거부 영수증.** 어댑터가 검증 단계에서 거부하면(exit 1) Grove가 dispatch 전에 쓴
  pending이 남아 같은 attach가 성공할 때까지 env가 잠겼다(destroy 불가). 실제로
  한 번 잠겼고, 워크트리를 같은 경로에 다시 만들어 같은 attach를 성공시켜 풀었다.
  이제 `{ok:false, mutated:false}` 마지막 줄이면 Grove가 그 dispatch의 pending을
  거둔다. 이전 pending의 재시도가 거부되면 그 pending은 남는다. 측정: 거부 뒤
  pending 0, finish 막히지 않음. stub 테스트 2/2, 가드 red 각 1.

### 실제 다중 서비스 Kubernetes 저장소 위에서 (2026-09-07)

지금까지 못 잰 경계였던 "서비스 여럿에 DB가 딸린 실제 프로젝트"에서 실행했다.
대상은 앱 13개, 클러스터 안 infra(MySQL·PostgreSQL·Redis·Kafka), Istio 게이트웨이,
그리고 **자기 overlay 도구를 이미 가진** 팀 저장소다. 그 도구는 `wt-<env>`
네임스페이스와 `<서비스>--<env>.<도메인>` 라우트로 얇은 overlay를 만든다. 기존
환경(살아 있는 overlay 하나, 공유 baseline)은 건드리지 않기로 하고, 같은
클러스터에 실험실 표식(네임스페이스 라벨)을 단 env만 만들었다가 지우는 경계로
진행했다.

프로젝트 쪽에 둔 것(그 저장소의 브랜치, 병합 안 함): Grove 프로파일(`proxy:
project`, 도메인 소유 scheme, attachable 8·shared_only 4는 그들 가이드의 허용 표
그대로), Dryad 프로파일, 그리고 어댑터. 어댑터는 그들 도구를 감싸 Grove 영수증을
내고, 이미지를 노드에 import하고, 자기가 라벨을 단 env만 status로 보고한다.

사람이 먼저 한 바퀴: create 1/1 → attach 1/1(import 포함 26초) → `<web>--g0` 200,
붙이지 않은 `<api>--g0`는 shared로 폴백 200, drift 0 → destroy. 네임스페이스·
라우트 수가 시작과 같고 기존 overlay는 그대로.

그 다음 자리 둘. 지시서에는 포트도 네임스페이스도 kubectl도 없다.

| --- | --- | --- |
| 변경 | 빌드 revision을 `<meta name="app-revision">`와 사이드바 한 줄로 서빙. 번들 검증 스크립트가 그 meta를 요구 | `/api/health`에 `pod`(호스트명)와 `revision`(빌드 상수) |

**막힌 곳 하나, 진짜 이음새 문제.** 두 자리 모두 첫 attach에서 그들 도구에 거부됐다.
"image tag must equal the full revision". 그 도구는 env를 **워크트리 하나와 revision
하나**에 묶고, create 때 호출자 cwd의 HEAD를 기록하며, attach 태그가 그 revision과
다르면 거부한다. Grove는 plan 시점(자리가 커밋하기 전, baseline에서)에 create를
한다. 두 모델이 어긋난 것이고 Dryad나 Grove의 결함은 아니다. 어댑터에서 풀었다.
attach 전에 기록된 revision과 이미지 revision이 다르면 env를 destroy하고 호출자
워크트리(`GROVE_CALLER_CWD`)에서 `create --revision <sha>`로 다시 만든 뒤 attach한다.
첫 attach는 잃는 것이 없고, 새 revision의 재attach는 env를 초기화한다. 그들
도구의 "one env, one revision" 규칙 그대로다. 첫 시도(create --revision만 재실행)는
"already belongs to another worktree or revision"으로 다시 거부됐고, 두 번째 수정이
맞았다. 두 자리는 지시서에 없던 이 원인을 정확히 짚어 blocked로 보고했고, 어댑터를
고친 뒤 같은 명령 재실행으로 Grove가 pending을 복구해 확정했다. 그동안 캐노피와
Dryad status는 `stalled`와 in-flight를 그대로 보였다.

정리: finish 둘 → Grove destroy → 그들 destroy. 네임스페이스 8, 공유 라우트 25,
실험실 라벨 0으로 시작과 같고, 기존 overlay와 공유 baseline 이미지는 그대로,
공유 이름들은 200. 노드에 import된 이미지 둘은 일부러 남겼다(그들 도구도 지우지
않는다).

관찰: `status --json`의 `hostnames`는 attach 여부와 무관하게 그 env의 모든
서비스 이름(12개)을 나열한다. `urls`가 이름을 찍는 것이지 라우팅을 증명하지
않는다는 Grove 문장 그대로지만, 화면에서는 붙은 것만 강조하는 편이 맞다.

### 분리된 실험실에서 다시: 별도 clone, 별도 클러스터, create_on: attach (2026-09-07)

같은 다중 서비스 저장소를 이번엔 **팀 환경에 닿지 않는 실험실**로 옮겼다. 세 겹을
분리했다. 별도 clone(팀 체크아웃의 `.git`에 남겼던 실험 브랜치는 지움), 별도 k3d
클러스터 `grove-lab`(팀 클러스터와 다른 호스트 포트·레지스트리, 게이트웨이는
8080), 그리고 그들 도구의 클러스터 고정을 실험실 브랜치에서만 환경변수로 뺀 것.
부트스트랩은 그들 `bootstrap`이 하는 일 그대로(k3d, Gateway API, Istio ambient,
base, infra 5개)를 실험실 컨텍스트로 밟았고, baseline은 팀 클러스터의 두 서비스
manifest를 읽기 전용으로 가져와 로컬 이미지 태그로 바꿔 올렸다. 실험 내내 팀
클러스터의 컨테이너 ID 6/6이 그대로였다(팀 클러스터에 새 env 하나가 생겼는데
팀 자신의 작업이며 이름·revision이 이쪽 것과 무관하다).

이 판의 목적은 이전 실행이 드러낸 이음새를 **어댑터 우회가 아니라 계약으로**
푸는 것이었다. Grove에 `overlay.create_on: attach`를 넣었다(`e243b73`). 자리의 첫
attach가 호출자 디렉터리에서 create를 자기 저널 mutation으로 실행하고 이어서
attach한다. 그들 도구는 create 때 cwd의 워크트리와 HEAD를 env에 묶으므로, 이제
env는 이미지가 나온 워크트리·revision에 처음부터 묶인다. 어댑터의 destroy·재생성
우회는 지웠고, revision이 다르면 거부만 한다.

사람이 먼저 한 바퀴(실험실 root에서): attach 하나로 create 1/1과 attach 1/1, env의
recorded revision == HEAD, 이름 200, 폴백 200, destroy 뒤 네임스페이스 7·라우트 2로
복귀. 그 다음 자리 둘(이전과 같은 과제, 지시서에 `:8080`만 추가).

| 관측 | s1 Claude Code (web) | s2 Codex (api) |
| --- | --- | --- |
| 첫 attach | 처음엔 거부됨. 어댑터의 create가 호출자 워크트리가 아니라 project root에서 돌아 env가 baseline HEAD에 묶임. 자리가 원인을 정확히 짚어 blocked 보고 | 같은 원인, 같은 진단 |
| 수정 | 어댑터 create를 `GROVE_CALLER_CWD`에서 실행(한 줄). 사람이 두 env를 destroy | |

| 자기 이름(`:8080`) | meta == HEAD 1, shared 0 | pod `wms-api-…`, revision == HEAD, shared엔 pod 없음 |
| 폴백 | 붙이지 않은 api는 shared | 붙이지 않은 web은 shared 빌드 |
| 규칙·테스트 | vitest 1241 + node:test 4, 가드 red | health 5, build runner 12, red 5+2 |
| session | 남김 | 남김 |

finish 둘 → 실험실 네임스페이스 7, 라우트 2, 실험실 라벨 0, baseline 두 서비스 200.
실험실 clone과 클러스터는 다음 실험을 위해 남겼다. 그들 도구의 테스트 64/64은
실험실 브랜치의 환경변수화 뒤에도 그대로다.

배운 것 하나. 계약으로 옮긴 뒤에도 어댑터가 create를 어느 cwd에서 실행하느냐가
남았고, 그것을 놓친 것은 사람(이 기록의 필자)이었다. 자리 둘은 첫 실행에서
그 원인을 코드 줄 단위로 짚었다. 이 왕복(두 자리 blocked → 한 줄 수정 → 같은

`in-flight`, `tracked`를 순서대로 보였다.

### 캐노피 2판: 워크트리마다 카드, 스킬 동사, 파일, 겹침 (2026-09-07)

[설계](../canopy-design.md)의 이음새 넷과 화면을 카탈로그 자리 둘로 병렬 구현했다.
데이터 자리(d1, Claude Code)는 `dryad.mjs`·`cli.mjs`에, 화면 자리(d2, Codex)는
`canopy.mjs`·`canopy.html`에.

| 이음새 | 실린 것 |
| --- | --- |
| 스킬 동사 | `DRYAD_ID`가 있는 프로세스가 상태를 바꾸는 동사(`overlay …--apply`, `setup`, `infra up|provision`)를 실행하면 CLI 진입점이 종료 코드와 함께 `cli` 저널 한 줄을 붙인다. 읽기 동사는 남기지 않고 `--` 뒤는 SHA-256 요약만 |
| 파일 변경 | 자리마다 `changes`: base, committed, uncommitted, counts, 200개 초과 시 truncated |
| 자리 아닌 워크트리 | 최상위 `worktrees[]`에 baseline과 자리 없는 워크트리까지, `seat: null`로 |
| 겹침 | 최상위 `overlaps[]`. 종료 코드를 바꾸지 않는다 |

화면은 프로젝트마다 헤더 한 줄과 워크트리마다 카드 하나다. 카드에 작업 첫 줄,
상태와 마지막 보고, env와 hostname(붙지 않은 것은 링크 없이 표시), 스킬 동사 개수,
파일 개수와 목록(겹치는 경로는 앞에 표시하고 먼저), 그리고 아래에 겹침 줄. 서버
렌더 첫 화면, 5초 폴링, loopback 전용, JS 없이도 렌더는 첫 판 그대로.

**병렬의 이음새가 실제로 드러났다.** 화면 자리는 데이터 필드를 fixture로만 알고
만들었고, 합친 뒤 캐노피 테스트 하나가 빨개졌다. 헤더가 `seats 1 · envs 1/1`에서
`seats 1 · worktrees 2 (1 unseated) · envs 1/1 · overlaps 0`으로 바뀐 것을 그
자리의 assertion이 몰랐기 때문이다. 사람이 한 줄 고쳤다. 그리고 두 자리가 같은
`skills/dryad/README.md`를 고쳤는데, 그 사실을 **이번에 만든 화면이 자기 자신을
만드는 동안의 겹침으로** 보여 주었다.

라이브 자리로 캡처하고 나서 읽기 문제 하나를 고쳤다. 카드가 같은 수백 자 보고를
status와 마지막 저널 줄에 두 번 찍어 카드가 아니라 기록이 됐다. 240자에서 자르고
같은 내용을 반복하지 않게 했다(전문은 저널과 `/api/state`에 그대로).

### 사람이 손으로 만들던 것을 스킬이 만들게 하다 (2026-09-07)

지금까지 "다른 사람은 못 쓴다"의 원인은 프로파일·어댑터·자리 지시서를 전부

### verify를 실제 어댑터에 돌려 나온 것 (2026-09-07)

`overlay verify`는 만든 그날 자기보다 먼저 쓰인 어댑터 둘에 돌렸고, 셋을 찾았다.
둘은 어댑터의 결함, 하나는 **verify 자신의 결함**이었다.

| 무엇 | 어디 | 결과 |
| --- | --- | --- |
| create가 멱등하지 않음 | 실험실 래퍼 어댑터 | 계약이 중단 후 재시도를 위해 요구하는 것. 이전 실행들은 env마다 create를 한 번씩만 해서 밟은 적이 없었다. 어댑터에서 "이미 내 것인 환경이면 성공을 보고"로 고침 |
| attach 서비스를 이미지와 무관하게 고름 | verify | 늘 `attachable[0]`을 붙여서, 다른 서비스의 이미지를 준 사람은 attach 사례를 통과할 수 없었다. `--service`를 넣고, 없으면 이미지 참조에서 서비스 이름을 읽게 함 |
| 어댑터에 계약 밖의 것을 요구 | verify | `overlay.attachable`은 앞문의 규칙이고 어댑터는 프로파일을 읽지 않는다. 어댑터가 미선언 서비스를 받아들이는 것을 실패로 세던 것을 보고로 바꿈 |

고치기 전 실험실 어댑터에 4/6, 고친 뒤 이미지와 서비스를 맞춰 **10/10**이다.
남은 규칙 하나가 실행에서 드러났다. 리비전에 묶는 어댑터에서는 **이미지를 만든
체크아웃에서 verify를 돌려야** 한다. 다른 디렉터리에서 돌리면 그 어댑터가 attach를
정당하게 거부한다. 어댑터 참고 문서에 적었다.

### 포트 충돌: Grove가 막으려던 일이 우리에게 일어났다 (2026-09-07)

verify를 정적 사이트에 돌린 뒤 실험실의 이름들이 전부 502가 됐다. 클러스터 안에서는
200, 노드 IP로도 200, 실험실 로드밸런서에서 노드로도 200인데 호스트에서만 502였다.
502 본문이 범인을 말했다. `no overlay for <web-host>:8080` — 실험실
게이트웨이가 아니라 **정적 사이트의 hostname 라우터**였다. 사이트 어댑터의 create가
그 라우터를 띄우는데 verify의 create가 그것을 실행했고, 라우터는 `127.0.0.1:8080`에,
실험실 게이트웨이는 `*:8080`에 묶여 있어 loopback 트래픽을 라우터가 가로챘다.

두 프로젝트가 각자 "프로젝트가 소유한 리스너"로 같은 8080을 골랐고, **둘 다 그 포트를
`addressing.ports.blocks`에 선언하지 않았다.** 이름으로 포트를 없애자는 스킬이 정작
자기 리스너의 포트를 등록부 밖에 두어 충돌한 것이다. 사이트 라우터를 8081로 옮기고
프로파일에 `proxy: 8081`로 선언했다. 그 뒤 두 프로젝트가 같이 뜬 채로 사이트 verify와
실험실 이름이 모두 정상이다.

여기서 나온 것: 이제 Dryad가 이 머신의 프로젝트 색인을 갖고 있으므로, Grove가
**선언된 포트끼리의 머신 단위 충돌을 검사**할 수 있다. 아직 구현하지 않았고 후보다.

### 처음 보는 저장소에 직접 심어 본 도입 시험 (2026-09-08)

"다른 사람이 문서만으로 할 수 있는가"는 사람이 필요해 계속 비어 있던 칸이다.
대신 조건을 정해 스스로 걸었다. **published 스킬 문서만 지시로 삼고, 내부 코드를
근거로 답을 대신 찾지 않고, 막힌 자리를 그때그때 적고, 끝을 `verify`와 자리 하나로
채점한다.** 대상은 한 번도 열어 본 적 없는 사내 모노레포(서비스 둘, 라이브러리 셋)를
실험실에 clone한 것이다. 원본 체크아웃은 건드리지 않았다.

결과: 프로파일을 심고, 자리 하나를 앉히고, 그 자리가 실제 개선을 넣고 검증까지
했다. 절차가 **두 곳에서 나를 잘못 이끌었고 둘 다 고쳤다**(`cc27882`).

| 단계 | 결과 |
| --- | --- |
| 서비스 찾기 | 마찰 없음. 라이브러리 셋이 모두 `dev` 스크립트를 갖고 있었지만 절차가 미리 경고한 함정이었다 |
| 포트·health | **마찰 1(중대).** 절차는 "요청을 한 번 해 보라"(2단계)를 "엔진 소유를 밝혀라"(5단계)보다 앞에 둔다. 시키는 대로 데이터베이스 이름이 붙은 엔드포인트를 먼저 요청했다. 결과적으로 무해했지만(핸들러가 질의를 하지 않고, 앱이 그 환경 파일을 읽지 않는다) 요청 전에는 알 수 없었다 |
| reflect | **마찰 2.** 첫 측정이 틀렸다. 재시작이 실패해 "안 돌던 서비스"를 재고 "반영 안 됨"으로 읽을 뻔했다. 로그를 본 덕에 잡았다 |
| 백엔드·엔진·주소 | 마찰 없음. 이름은 해석되지만 404였고, 리스너가 없다는 증거대로 `proxy`를 비웠다 |
| overlay 판단 | **아니오.** 서비스는 둘이지만 격리된 빌드·라우팅이 없고 포트가 소스 리터럴이다. 절차가 시키는 대로 `overlay: none`. 이 프로젝트에 대한 정직한 답이다 |
| 자리 하나 | 심으면서 드러난 결함("API 포트를 소스에서만 바꿀 수 있다")을 그대로 과제로 냈다. 자리가 `PORT`를 읽게 고쳤고, 사람이 두 인스턴스를 3002와 3102에 동시에 띄워 각각 200을 확인했다 |

절차에 넣은 수정 둘. **health 경로는 요청하기 전에 그것이 무엇에 닿는지 읽는다**
(엔드포인트 이름은 증거가 아니다. 핸들러와, 서비스가 실제로 읽는 환경 파일을
따라간다. 후보가 데이터스토어 뒤에만 있으면 5단계를 먼저 한다). 그리고 **reflect를
잴 때 비교의 양 끝에서 서비스가 살아 있는지 확인한다**(안 도는 서비스에 대한 실패
응답은 반영 안 된 편집과 똑같이 생겼다).

심는 것만으로 저장소가 갖고 있지 않던 사실 셋이 나왔다. API 포트를 소스에서만 바꿀
수 있다는 것, 프로젝트의 `dev` 명령이 API를 아예 띄우지 않는다는 것(그 앱에 `dev`
스크립트가 없다), 기본 데이터베이스 이름이 한 머신의 두 프로젝트가 공유할 만큼
일반적이라는 것. 첫 번째는 그날 자리가 고쳤다.

남은 한계는 정직하게: 나는 이 문서들을 쓴 사람이라 "처음 보는 사람"을 완전히
연기할 수 없다. 이 시험이 증명한 것은 **절차가 처음 보는 저장소에 대해 끝까지
실행 가능하고, 실행하면 결함이 드러난다**는 것이지, 사람의 학습 시간이 아니다.

### 잴 수 없는 것과 재지 않을 것

- **:80 리스너.** macOS에서 root가 필요하고 이 머신의 `sudo`는 비밀번호를 요구한다.
  라우터는 8080에 듣는다. "포트를 기억하지 않는다"는 머신에 하나 남은 포트까지
  없애야 완성이며, 그것은 리스너를 root로 두는 운영 결정이지 Grove 코드가 아니다.
- **생산성 효과.** 시간 절감이나 충돌 감소는 이 저장소가 주장하지 않는 것이고,
  하루의 실행으로 잴 수 있는 것도 아니다. 제품 방향 문서가 같은 말을 한다.
- **실제 에이전트 도구의 회귀 검사.** 자격증명과 도구가 필요하고 런처는 설계상
  밖이다. 위 하네스가 계약 쪽을, 수동 실행 셋이 도구 쪽을 맡는다.
- 공유 백엔드(k3d, compose)의 adapter 동시 실행. 이전과 같은 경계.
- 다른 호스트가 잡은 락의 liveness. 레지스트리가 머신 로컬이라 `unknown`으로만
  표시한다.
